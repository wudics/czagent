# 附件处理

> 对应 PLAN.md 决策 #7、#12。支持类型：txt、markdown、docx、xlsx、pptx、pdf、图片（jpg/png/webp/gif）等。

## 1. 处理策略（决策 12：混合）

| 类型 | 策略 |
|---|---|
| txt / md | 解析为文本，**内联**进 user 消息 part（若超阈值转引用） |
| docx / xlsx / pptx / pdf | 解析为文本；解析后文本 **< 50KB** → 内联；**≥ 50KB** → 存会话 temp 目录，消息放文件引用 part，agent 用 read 工具按需读取 |
| 图片 | 作为 `image_url` 交给**图像理解模型**（vision）；模型无视觉能力时降级为文件引用（P2：可调图像理解模型理解后回填） |
| 其他/超上限 | 拒绝并提示（限制大小见 §3） |

- 一次上传多个文件：各自解析，按上述规则分别内联或引用。
- 所有内联文本在消息里标记来源（`<file: name>` 前缀），便于模型区分。

## 2. 解析器（决策 7：全部 Node 库）

| 格式 | 库 | 要点 |
|---|---|---|
| txt/md | 原生 | 直接读取 UTF-8（BOM 容错） |
| docx | `mammoth` | 提取段落文本（图片忽略/占位） |
| xlsx | `exceljs` | 遍历 worksheets → 行数组 → 文本表格化（含表头） |
| pptx | `unzip` + XML 解析 | 读 `ppt/slides/*.xml` 提取文本框（参考 opencode `apply_patch` 同族的轻量 XML 方案） |
| pdf | `pdfjs-dist` | 提取每页文本（纯文本，忽略版式） |
| 图片 | 原生 | 读取元数据（尺寸/类型/大小），正文内容走 vision |

> 每个解析器独立模块、独立单测；解析失败 → 降级为文件引用并提示"该附件无法解析为文本，已作为文件引用"。

## 3. 大小限制

| 维度 | 限制（可配） |
|---|---|
| 单文件 | 默认 20 MB |
| 图片 | 默认 10 MB / 张（超限压缩或拒绝） |
| 内联文本 | 50 KB（解析后） |
| 单会话附件总数 | 默认 50 个（防 temp 堆积） |

## 4. 临时存储与清理

- 目录：`app.getPath('temp')/czagent/attachments/<sessionId>/`（跨平台统一逻辑路径）。
- 生命周期：
  - 上传 → 落盘 + `attachments` 表记录。
  - 内联附件：解析完成后可立即删（内容已入消息），或统一清理。
  - 引用附件：会话活跃期间保留（agent 可能读取）。
  - **清理时机**：会话删除、应用退出时清理过期 temp；启动时扫描孤儿目录清理（保留策略：最近 7 天活跃会话的附件保留）。
- 安全：附件路径不做任何执行操作；渲染层预览仅白名单扩展名。

## 5. 与对话的衔接

- `SendMessageInput.attachments?: string[]`（attachment ids）。
- 发送时主进程按 §1 策略解析并组装进 user 消息 parts（文本 part / 图片 part / file 引用 part）。
- 针对附件的追问：附件引用 part 保留在历史中，后续消息可继续引用同一附件（如"再分析一下刚才那个 PDF 的第 3 章"）。

## 6. 图片部分（P2 视觉工具衔接）

- 图片 part 进入模型：`content: [{ type:'image_url', image_url:{ url:'data:image/...;base64,...' } }]`。
- 需要图像理解模型时：图片优先路由到会话配置的 image-understanding 模型实例（决策 6 的能力工具）；无该配置时走当前对话模型（若支持视觉）。
