# 034 · 手动压缩 + 右栏上下文用量百分比

日期：2026-09-07
前置：用户三问引出需求——①压缩如何进行（纯自动，runLoop 每轮检测）；②压缩后聊天内容是否显示（DB/UI 全量保留，checkpoint 渲染为折叠条）；③是否与显示冲突（不冲突，压缩是纯请求侧概念）。顺势提两点改进：RightPanel 显示 token 上下文百分比 + 按钮确认后手动压缩。

## 决策（用户拍板）

- 确认交互复用现有 `ui/dialog.tsx`（与新建会话风格一致），不用 window.confirm。
- 手动压缩**不受**设置里"自动压缩"开关（auto）限制——auto 只管自动触发；contextLimit=0 时传极大预算，按尾部预算钳制（15k）+ 200 条上限压缩。
- 百分比分子用 `usageTotal` 口径（input+output+reasoning+cacheRead+cacheWrite 五项全加），与自动压缩判定信号一致；RightPanel 原"Token 消耗"是累计 SUM 值，不能混用。

## 变更

- **契约**（`core/src/provider.ts`）：`AgentProvider.compactSession(sessionId): Promise<boolean>`（返回是否实际压缩）；`SessionEvent` 新增 `session.compacted`（携带 checkpoint 消息）。不用 `message.complete` 推送 checkpoint——该事件会把 chat store 的 `replying` 置 false，自动压缩发生在运行中会误启用输入框。
- **核心**（`core/src/node/session-manager.ts`）：
  - `maybeCompact` 改返回 `Promise<boolean>`（old 区为空/摘要失败 → false），checkpoint 落库后 emit `session.compacted`——**顺带修复原有滞后瑕疵**：自动压缩的 checkpoint 此前直写 DB 不发事件，运行中界面要重开会话/翻页才能看到折叠条。
  - 新增 public `compactSession`：校验会话存在且 status=idle（运行/排队中抛错）→ 解析 model/provider → `historyWindow` + `pruneHistory` 取窗口 → `usable = compactionUsable() ?? MAX_SAFE_INTEGER`（绕过 auto 开关）→ 复用 `maybeCompact`。非破坏语义不变：旧消息保留 DB，仅请求窗口跳过。
- **IPC 链**：`shared/ipc.ts` 加 `session.compact`；preload / main registerIpc 各一行；mock provider 补实现（<8 条返回 false，尾部保留最新消息插演示 checkpoint 并 emit）。
- **渲染层**（`stores/chat.ts` + `RightPanel.tsx`）：
  - chat store 加 `compacting` 状态 + `compact()`（replying/compacting 时 no-op 返回 false，finally 兜底复位）；`session.compacted` 处理：checkpoint **按 createdAt 时间序插入**消息列表（向上翻页后旧区消息仍在列表上方，不能尾部 append）。
  - RightPanel 新增"上下文"区块（Token 消耗下方）：分子 = 最近一条带 `tokens` 的 assistant 消息经 `usageTotal` 折算（零新 IPC，`message.complete` 已带 tokens）；分母 = settings store `models` 按 `session.modelId` 查 `contextLimit`；进度条 + `42% · 84.2k / 200k`，≥90% 转红色告警；未知窗口显示提示，无数据显示 —。"压缩上下文"按钮（outline/sm，FoldVertical）→ Dialog 确认 → 执行；压缩中/回复中禁用；结果 4 秒内联提示（完成/暂无可压缩/失败原因，运行中错误映射专用文案）。
  - `core/src/index.ts` 补导出 `usageTotal`（纯函数，浏览器入口可用）。
- **i18n**：zh-CN / en-US 增 `panel.context / contextOf / contextUnknown / compact*` 系列 key。

## 验证

- `pnpm typecheck` ✅（core + desktop）· `pnpm test` ✅（core 18）· `pnpm --filter @czagent/desktop build` ✅（renderer 1922 模块）。
- 待 Electron 冒烟：长会话回复数轮 → 右栏百分比随回复增长 → 压缩确认 → 折叠条即时出现、百分比回落；运行中点击按钮的禁用与提示。

## 边界与后续

- 压缩中不可停止（未注册进 `aborts`，摘要为单次 LLM 调用通常数秒内完成）；后续可考虑纳入 stop 链路。
- 手动压缩与运行中会话互斥（status=idle 才可执行），与 sendMessage 防重入口径一致。

# 034.1 · 上下文仪表 B 方案 — 主进程权威口径

日期：2026-09-07
前置：用户实测反馈——22%（216.4k / 1000k）点手动压缩后百分比不变，但"历史已压缩"折叠条正常出现。根因：百分比分子 = 最近一条 assistant 消息的 `tokens`（上次请求规模），压缩不重写历史 tokens，checkpoint 本身不带 tokens，须等下一次回复落库才回落。属 034 已知近似，但反直觉。

## 决策（用户拍板）

- 方案比选：**A**（渲染层从 checkpoint 起累加 `estimateMessageTokens`，漏 system prompt/请求侧 prune，改动 2 文件）vs **B**（主进程在与真实请求同一条构建路径上算权威值，经事件推送）→ **选 B**：1000k 大窗口 + 工具/MCP 会持续增长，`usageTotal` 口径本身还系统性低估（不含 system prompt/env/工具定义），B 一步到位让百分比具备仪表价值。

## 变更

- **契约**（`core/src/provider.ts`）：`SessionContext { used: number; limit: number }`；`AgentProvider.getSessionContext(sessionId)`（切换会话初始拉取）；`session.context` 事件收敛为 `{ used, limit }` 自包含形态。
- **与并行实现的合并**：v0.1.0 已含一版逐轮用量机制——`session.context { usage: Usage }`（`reportUsage(emitContext)` 发射）+ chat store `contextUsage` + RightPanel 消息回退扫描。本轮**统一拆除**旧形态（provider 重复变体、reportUsage 第三参、调用点 `true`、mock 旧发射、store/RightPanel 消费端），收敛为单一权威口径，避免双口径漂移。
- **核心**（`core/src/node/session-manager.ts`）：一个计算器 + 四个发射点，同一口径 `est = max(estimateRequestTokens, 上次真实 usage)`（与自动压缩判定完全一致，含 system prompt/env/MCP 说明）：
  | 发射点 | 时机 | 成本 |
  |---|---|---|
  | runLoop 压缩检测后 | 每轮请求构建时，直接 emit 已算好的 `est` | 零额外计算 |
  | finalizeMessage | 每次回复落库后，`usageTotal(usage)`（API input 已含全部请求内容）让仪表随回复跳动 | 免费 |
  | compactSession | 手动压缩成功后全量重算 → **百分比立即回落** | 低（用户触发） |
  | `getSessionContext` | IPC，会话打开时 | 低 |
  - `computeContext(sessionId)`：解析会话/模型/agent → `historyWindow`+`pruneHistory` → envBlock/MCP 说明 → `buildRequestMessages` 估算，模型缺失返回 null。
  - **顺带重构**：envBlock 构建提取为 `buildEnvBlock`（runLoop 与估算共用，消除重复）；MCP 工具清单提取 `mcpToolsFor` + 纯函数 `mcpNoteOf`；`lastUsageTokens` 提为模块级（runLoop/估算共用）。
- **渲染层**：chat store `contextUsage: Usage|null` → `context: SessionContext|null`（open 时 IPC 拉取 + 事件实时刷新）；RightPanel 删除本地估算/`models` 查表/消息扫描，改读 `context`（进度条、≥90% 红色告警、压缩按钮/Dialog 不变）。
- **mock**：`contextUsed` Map 维护（回复后 = 累计 usageTotal + 8k 近似 system prompt；压缩后回落 12~16k），`getSessionContext` + `emitContext` 对齐真实语义。

## 验证

- `pnpm typecheck` ✅（core + desktop）· `pnpm test` ✅ · `pnpm --filter @czagent/desktop build` ✅。
- 待 Electron 冒烟：发送回复 → 仪表随请求构建/落库两次刷新；手动压缩 → 立即回落至 ~2%（尾部 15k + 摘要）；切换会话 → 初始值正确；后台会话事件不串扰（store sessionId 守卫）。

## 边界与后续

- runLoop 与 finalize 双发射：构建时 est（含完整请求开销）与落库后 usageTotal 交替校准，取值口径略有差异（估算 vs 真实），仪表呈小幅波动属正常。
- `getSessionContext` 每次全量重算（300 条窗口查询 + 字符串估算 + MCP 清单），仅会话打开/手动压缩触发，不在请求热路径。

## 修正（同日 · 用户实测反馈）

- **手动压缩后百分比不立即回落**：`computeContext` 与 runLoop 发射点的 `max(估算, 上次真实 usage)` 混合口径在窗口含 checkpoint 时失效——keep 区最近一条 assistant 消息仍带压缩前请求的 tokens（216.4k），max 后发出的仍是旧值，须等下一轮 finalize 纠正。修正：**窗口含 checkpoint 时仪表改用纯请求估算**（上次 usage 口径仅在全量窗口兜底启发式偏差）；溢出检测的 est 保持 max 混合口径不变，压缩判定语义零影响。效果：点压缩 → 提示成功的同时立即回落到新窗口规模（尾部 15k + 摘要）。
- **UI**：压缩结果提示与按钮间距 `mt-1.5` → `mt-2.5`。
