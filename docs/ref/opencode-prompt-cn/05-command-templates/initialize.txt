为这个仓库创建或更新 `AGENTS.md`。

目标是一个紧凑的指令文件，帮助未来的 OpenCode 会话避免错误并快速上手。每一行都应该回答："没有帮助的话，agent 会不会很可能错过这个？" 如果不会，就把它省略。

用户提供的关注点或约束（请遵守这些）：
$ARGUMENTS

## 如何调查

先阅读价值最高的来源：
- `README*`、根清单文件、工作区配置、lockfiles
- 构建、测试、lint、格式化、typecheck 和 codegen 配置
- CI 工作流和 pre-commit / 任务运行器配置
- 现有的指令文件（`AGENTS.md`、`CLAUDE.md`、`.cursor/rules/`、`.cursorrules`、`.github/copilot-instructions.md`）
- 仓库本地的 OpenCode 配置，如 `opencode.json`

如果在阅读配置和文档后架构仍不清楚，检查少量有代表性的代码文件，找到真正的入口点、包边界和执行流程。优先阅读解释系统如何连接起来的文件，而不是随机的叶子文件。

优先使用可执行的真相来源而不是文字说明。如果文档与配置或脚本冲突，相信可执行来源，只保留你能验证的内容。

## 要提取什么

寻找在这个仓库工作的 agent 最有价值的信号：
- 确切的开发命令，尤其是非显而易见的命令
- 如何运行单个测试、单个包或一次聚焦的验证步骤
- 在重要时的必需命令顺序，如 `lint -> typecheck -> test`
- monorepo 或多包边界、主要目录的所有权、真实的 app/库入口点
- 框架或工具链的怪癖：生成代码、迁移、codegen、构建产物、特殊 env 加载、dev servers、基础设施部署流程
- 与默认不同的仓库特定风格或工作流约定
- 测试怪癖：fixtures、集成测试前提条件、快照工作流、必需服务、不稳定或昂贵的套件
- 值得保留的现有指令文件中的重要约束

好的 `AGENTS.md` 内容通常是来之不易的上下文，需要阅读多个文件才能推断出来。

## 问题

只有当仓库无法回答某件重要事情时，才向用户提问。最多使用一次 `question` 工具，一次简短的批次。

好问题：
- 未文档化的团队约定
- 分支 / PR / 发布预期
- 已知但未写下来的缺失设置或测试前提条件

不要问仓库已经说清楚的事情。

## 编写规则

只包含高信号、仓库特定的指导，例如：
- agent 原本会猜错的确切命令和快捷键
- 从文件名看不出来的架构说明
- 与语言或框架默认值不同的约定
- 设置需求、环境怪癖和操作陷阱
- 对重要的现有指令来源的引用

排除：
- 通用软件建议
- 长教程或详尽的文件树
- 显而易见的语言约定
- 投机性声明或任何你无法验证的内容
- 更适合存储在通过 `opencode.json` `instructions` 引用的另一个文件中的内容

拿不准时，省略。

偏好短章节和项目符号。如果仓库简单，保持文件简单。如果仓库很大，总结那些真正会改变 agent 工作方式的少数结构事实。

如果 `AGENTS.md` 已存在于 `${path}`，就地改进它，而不是盲目重写。保留已验证有用的指导，删除填充内容或过时声明，并与当前代码库对账。
